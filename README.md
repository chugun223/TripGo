# TripGo - лабораторная работа 2

HTTP-сервис для управления поездками.
В лабораторной работе 2 сервис разделён на архитектурные слои, добавлены unit и интеграционные тесты, структурное логирование, метрики и распределённая трассировка через OpenTelemetry.


## Запуск

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect

make migrate
make run
```

## Команды
```bash
make generate          # перегенерировать go код из OpenAPI
make migrate           # применить миграции
make migrate-down      # откатить последнюю миграцию
make run               # запустить сервис
make test              # unit тесты с -race и покрытием
make test-integration  # интеграционные тесты с PostgreSQL
make lint              # проверка golangci-lint
```

## Архитектура

Сервис разделён на слои с однонаправленными зависимостями. Бизнес-логика отделена от HTTP, PostgreSQL и OpenTelemetry.

Основные компоненты:

- cmd/trip-service - точка входа, запуск сервиса и корректное завершение работы
- internal/config - чтение и проверка конфигурации из переменных окружения
- internal/container - создание и связывание зависимостей приложения
- internal/domain/trip - доменная модель поездки, бизнес-правила, переходы статусов и доменные ошибки
- internal/model - структуры для передачи данных между слоями
- internal/usecase/trip - сценарии создания, получения и завершения поездок
- internal/http - HTTP-обработчики, валидация запросов, преобразование ответов и middleware
- internal/http/domainerror - единое преобразование доменных ошибок в HTTP-ответы
- internal/repository/trip - реализация доступа к данным поездок и истории статусов
- internal/infra/postgres - подключение к PostgreSQL и управление транзакциями
- internal/infra/telemetry - настройка OpenTelemetry и регистрация метрик
- internal/infra/observability - декораторы Usecase для записи бизнес-событий и метрик
- internal/generated - код, сгенерированный по OpenAPI


HTTP-обработчики вызывают Usecase через интерфейсы. Usecase выполняют бизнес-сценарии и обращаются к репозиториям и менеджеру транзакций через интерфейсы.

Интерфейсы объявляются на стороне потребителей в файлах contract.go. Это позволяет заменять реализации зависимостей и использовать моки при тестировании.

Все конкретные реализации создаются и связываются в internal/container.

Для логирования бизнес-событий и обновления бизнес-метрик используются декораторы из internal/infra/observability. Они оборачивают Usecase, поэтому бизнес-логика не зависит напрямую от OpenTelemetry и инфраструктурного логирования.

## Обработка ошибок

Доменные ошибки определены в internal/domain/trip.

Преобразование ошибок в HTTP-ответы выполняется централизованно в internal/http/domainerror.

## Тестирование

Для проверки сервиса используются:

- Unit-тесты доменной модели
- Unit-тесты Usecase с gomock
- Тесты HTTP-обработчиков с httptest
- Тесты преобразования доменных ошибок
- Интеграционные тесты репозиториев с реальным PostgreSQL
- Тесты декораторов Observability

Запуск:
```bash
make test
make test-integration
make lint
```
make test запускает тесты с детектором гонок и выводит покрытие кода.

make test-integration запускает интеграционные тесты с билд-тегом integration, проверяя работу с PostgreSQL, в том числе откат транзакции при ошибке.

## Observability

Для наблюдаемости сервиса используется OpenTelemetry.

### Логирование

Логи формируются через log/slog в формате JSON и выводятся в stdout.
HTTP middleware записывает метод, шаблон маршрута, статус ответа, длительность обработки и идентификаторы trace_id и span_id.
Бизнес-события создания и завершения поездок логируются отдельно.

### Трейсы

HTTP-запросы инструментируются через otelhttp, обращения к PostgreSQL - через otelpgx.

Трейсы отправляются по OTLP в коллектор и доступны для просмотра в Jaeger.

HTTP-спаны именуются по методу и шаблону маршрута, например POST /api/v1/trips. Внутри трейса можно увидеть операции PostgreSQL.

### Метрики

Сервис экспортирует следующие метрики:
- http.server.request.duration - длительность HTTP-запросов
- http.server.active_requests - количество обрабатываемых запросов
- db.client.operation.duration - длительность операций с базой данных
- tripgo.trips.created - количество созданных поездок
- tripgo.trips.completed - количество завершённых поездок

Метрики доступны в Prometheus и Grafana через коллектор OpenTelemetry.

Адреса Jaeger, Grafana и Prometheus можно получить командой:
```bash
tripgoctl connect
```

## Решения
### С лабораторной работы №1
#### Уровень изоляции транзакций

Для транзакций выбран уровень изоляции Read Committed.
Он обеспечивает чтение только зафиксированных изменений.


#### Менеджер транзакций

Менеджер транзакций предоставляет метод Do(ctx, fn). Он открывает транзакцию PostgreSQL, сохраняет её в контексте и передаёт производный контекст callback функции.
Если callback завершается без ошибки, менеджер фиксирует транзакцию с помощью COMMIT. Если callback возвращает ошибку или вызывает панику, менеджер выполняет ROLLBACK.


#### Атомарность создания поездки

Создание поездки выполняется в рамках одной транзакции:
Новая поездка сохраняется в таблице trips.
Начальный переход статуса записывается в trip_status_history.
Если любая операция завершается ошибкой, транзакция откатывается. Поэтому поездка не может сохраниться без соответствующей записи в истории статусов.


#### Запрет нескольких активных поездок у водителя

Для обеспечения ограничения на уровне PostgreSQL используется частичный уникальный индекс trips_active_driver_uidx по полю driver_id для строк со статусом active.
Таким образом база данных не позволяет одному водителю иметь две активные поездки, в том числе при одновременных запросах.

### С лабораторной работы №2
#### Разделение приложения на слои

Для разделения бизнес-логики и инфраструктуры приложение организовано по слоям Domain, Usecase, HTTP и Repository. Зависимости передаются через интерфейсы, объявленные на стороне потребителей. Создание конкретных реализаций и связывание компонентов выполняется в internal/container.
Это позволяет тестировать бизнес логику независимо от PostgreSQL и HTTP.


#### Организация Observability

Для сбора логов и бизнес-метрик используются декораторы Usecase, расположенные в internal/infra/observability. Они оборачивают бизнес-сценарии создания и завершения поездок, не изменяя их основную логику.
HTTP-запросы и обращения к PostgreSQL инструментируются через OpenTelemetry. Это позволяет отслеживать выполнение запросов в Jaeger и анализировать метрики в Grafana.
